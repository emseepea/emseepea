# Feedback description delivery outcome

Approved target: end of Sunday, 25 October 2026, Australia/Sydney.
Tracking: [issue #179](https://github.com/emseepea/emseepea/issues/179).

## Outcome

Adopters can install a released feedback package whose default description
limits collection to the application operation and whose public configuration
supports accurate application-specific wording while preserving native feedback.

## Acceptance evidence

| Observable outcome | Required evidence |
| --- | --- |
| Default describes operation-specific feedback | Published discovery retains qualifying triggers, success disclosure, objections and privacy guidance; excludes unrelated conversation and general behavior |
| Adopter supplies application-specific wording | Public TypeScript option, configuration validation and unchanged wording in discovery |
| Native behavior remains intact | Public and protected protocol journeys compare every other discovery field and exercise validation, delayed durable receipt and backend failure |
| Adopter can use the feature | Package README, website guide and release note explain replacement wording and accurate storage and retention |
| Package is released | Required local checks, exact-source Quality, semantic Release, registry verification, Publish and fresh installed-package verification |

## Delivery sequence

1. Correct the default and add the supported option with public-boundary tests.
2. Review architecture, privacy, cognitive accessibility and wording; address findings.
3. Run the required clean committed-head qualification and benchmark.
4. Use the existing release pipeline, verify npm publication and install the released package independently.
5. Record exact versions, source and workflow evidence against the outcome.

The scope includes the native `defineFeedbackSubmission` constructor. Collection
submission tools and their existing descriptions are unchanged. Storage adapters,
collection policy and client approval controls are outside this metadata change.
The accepted calculator scan is prior evidence for that application, not a
promise of universal marketplace acceptance or automatic invocation behavior.

## Current evidence

The new public and protected tests pass discovery comparisons on all six
supported protocol versions and verify validation, deferred receipt and backend
failure. Runtime configuration rejects blank and non-string descriptions.
Release and independent installed-package verification remain pending.
